# Work and pull request reconciliation

> **Experimental implementation of issue #312.** Provider facts, caller declarations, reported outcomes and scope ownership remain separate. A merge never completes Work or releases its reservation. Synthetic tests exercise SQLite and PostgreSQL; live forge and deployed harness behavior remain unqualified.

Use the durable version-2 declarations and reconciliation surfaces for structured prerequisites. The existing version-1 report remains compatible for older clients. Reading either report never acknowledges a delivery or applies a reconciliation.

## Reservation visibility and authority

Every unfinished Work item holding a reservation stays visible in current overview and briefing pages, including merged Work. Its overlap remains visible within the normal page and completeness bounds. `settled_count` counts only nonholding Work hidden by the legacy branch-merge heuristic. Hiding never releases a claim, and branch reuse or fork branches cannot grant completion or scope authority.

Durable reconciliation records `held_owner_decision_required` when an exact declared Work link merged but scope is still held. An explicit retain decision remains `explicitly_retained`; released Work remains released. Existing lifecycle transitions and their actor authorization decide release, retain or completion. Lease expiry and recovery policy belong to the separate lifecycle work, not merge evidence.

## Compatibility version-1 report

`GET /v1/hub/standup/work/{id}/reconciliation` and `agentscm work reconcile <id>` retain their strict response fields and enum values. The report joins one caller-reported compatibility PR link, exact retained provider merge facts, open or retained closed observations, reported outcome, reservation and legacy `depends_on` hints. Read-only tokens may read; inaccessible Work returns the same not-found answer as unknown Work. Tokens never appear in the report.

A prerequisite is satisfied only by one retained merge whose independently provider-confirmed head matches its explicit link. `forge_pull` merge rows carry that confirmation. `tracked_publication` rows retain the published commit, which may differ from the PR head that merged; their heads remain unknown with `merge_head_unconfirmed` unless a retained, unambiguous individual provider read confirms the raw provider PR number, stable base repository ID and merge SHA with a valid actual head. A normal synchronized merged tombstone can supply this confirmation even when an immutable publication merge row already exists. Missing, malformed, conflicting or mismatched observations cannot qualify it. A changed or ambiguous merged head remains unknown. Closed-unmerged observations are expressed as the existing unknown status plus `closed_unmerged_observed`; missing, malformed or ambiguous observations remain explicit limits. Equal-timestamp conflicting PR observations become unknown until a strictly newer read. Retained merge facts remain facts during an outage; missing occurrence timestamps carry `merge_time_unknown`.

Version 1 still has separate reads (`atomic_snapshot: false`) and a final Work recheck. Coverage is a catch-up preview that can run the existing publication backfill. Its digest excludes blocker and open-observation clock fields. Its reassessment flag is derived, and it supports only the independent single-link compatibility slot (`single_pr_link_only`). Legacy checkpoint omission can clear legacy relation hints; the durable declarations below survive it. New clients should use version 2 for persisted results and multiple explicit conditions.

## Provider identity and uncertain evidence

Merge lookups use provider, host, stable repository ID and PR number, never just a branch. Fork and branch reuse therefore cannot satisfy a different explicit target. Repository renames preserve the stable evidence namespace; Work still stored under an old repository name needs the existing `work repair-repository` operation before a token for the renamed repository can read it. Legacy unbound or unlinked conditions remain unknown until an evidence target is declared.

A closed-unmerged PR is never success. A newer open observation supersedes its tombstone; older observations cannot resurrect stale state. Conflicting equal read stamps stay ambiguous. Multiple or partial PRs are independent exact-head conditions: one merge cannot satisfy another condition, and all declared conditions satisfied still does not establish whole-task implementation or completion. Missing coverage, retention gaps and unknown times stay explicit. Retained observations are not a live forge mirror; missed synchronization is unknown until another provider read.

## Durable caller declarations

The separate `GET /v1/hub/standup/work/{id}/declarations` response has `schema_version: 2`. It contains a caller-declared set of additional PR links and typed prerequisite conditions. It does not establish provider facts or claim that a Work item completed. Read-only tokens can read it. A foreign repository receives the same not-found response as unknown Work. The compatibility single-link endpoint owns an independent `compatibility_link` slot; setting or clearing that slot cannot erase additional links or conditions.

`POST /v1/hub/standup/declarations` accepts `work_id`, `operation_id`, `generation`, `session`, `expected_updated_seq` and a complete `declarations` replacement. Only the current lead token/session may write. A successful mutation advances the Work sequence without rewriting its progress report, blocker, outcome or reservation. Exact retries return the original receipt and current view; operation ID reuse for a different canonical request is refused. Link and condition order is canonicalized by stable `id`. Explicit empty arrays remove the corresponding declarations.

Each additional link has an `id` and a `target` containing the authorized stable `repository_id`, PR `number` and full lowercase `head_sha`. Each prerequisite has an `id` and a tagged `requirement`: `merged_pull_request` names a readable prerequisite `work_id` and an exact `target`; `legacy_work` names a dependency whose evidence target has not been declared. IDs are bounded visible labels. Explicit updates allow at most 32 additional links and 32 conditions. Imported legacy dependencies may retain up to the existing 100-relation bound; none is silently dropped. All PRs in a partial or multiple-PR Work remain separate declarations; satisfying all declared merge conditions still cannot prove whole-task success.

The named migration copies existing `depends_on` relations once into deterministic `legacy-<work-id>` conditions with `legacy_work` requirements. New Work starts seed the same independent record, including an empty record. These conditions are unbound caller reports and remain unknown until explicitly replaced with evidence-targeted requirements. Legacy checkpoint omission still clears its legacy relation hints, but cannot delete the durable declaration record. The initial `declaration_seq` is the Work sequence at migration or admission; later updates use their committed event sequence. Every Work has a declaration record, so there is no absent-record sequence sentinel. The mutation records the existing `work_pr_link` audit kind with `operation: declarations_set` for history and catch-up compatibility.

CLI equivalents are `agentscm work declarations <work-id>` and `agentscm work declarations-set --request <json-file>`. The v1 read-only reconciliation response remains wire-compatible and still projects legacy `depends_on`; evaluation and reassessment use the separate fenced apply operation below.

## Durable evaluated reconciliation

`GET /v1/hub/standup/work/{id}/reconciliation-v2` reads the durable v2 evaluation. `POST /v1/hub/standup/reconciliation` explicitly evaluates retained server evidence and persists its result. The request contains only `work_id`, `operation_id`, `generation`, `session`, `expected_updated_seq` and `declaration_seq`; callers cannot submit evidence or evaluated states. The current lead session must authorize the operation. An exact retry returns its committed receipt and the latest view; reusing its operation ID for another request is refused. CLI equivalents are `agentscm work reconciliation <id>` and `agentscm work reconcile-apply --request <file>`.

Both stores gather declarations, prerequisite Work versions, exact merge rows, retained PR observations, source coverage and retention boundaries in one transaction. SQLite uses an immediate write transaction; PostgreSQL uses a repeatable-read transaction and the existing Work/capacity locks. A concurrent later report or declaration update cannot be overwritten. The successful operation advances the Work sequence for fencing and records `work_pr_link` audit history with `operation: reconciliation_applied`; it does not change the original progress report, blocker, Work state, reported outcome, reservation or meaningful-report clock.

The persisted snapshot binds the resulting Work sequence, declaration sequence and a deterministic digest of the retained provider and prerequisite facts. `retained` is historical evidence. `current` is present only while those three bindings still match a new atomic read. A later checkpoint, prerequisite report, declaration/link change, source poll, observation or retention change makes the snapshot stale, with explicit reasons and no current condition success. Poll timestamps can invalidate a snapshot even when the apparent PR state is unchanged. These bindings describe retained observations, not live forge freshness; a missed webhook cannot be detected before another provider read.

Each exact-head merge condition is independent. One matching retained merge satisfies that condition even during an outage; changed or ambiguous merged heads remain unknown. An open or explicitly closed-unmerged observation establishes a negative only with complete observed coverage and no merge-retention gap. Malformed, missing or equal-stamp-ambiguous observations remain unknown. Missing merge occurrence time is recorded as `merge_time_unknown`, separate from the retained merge fact. Legacy unbound conditions remain unknown. All conditions satisfied is not whole-task completion.

A satisfied condition clears only its own structured obstruction. If a free-text blocker remains, the operation records a stable reassessment request bound to that blocker report, condition declaration and exact merge evidence. It never rewrites or clears the free-text blocker or unrelated conditions. Reapplying identical evidence uses the same request identity; audit history preserves earlier requests when a later report changes them. The derived next action names the remaining conditions or asks for blocker reassessment. A merged Work link with a held reservation reports `held_owner_decision_required`; an explicit retained basis remains `explicitly_retained`. Remedies come from the existing lifecycle policy and still require that transition's actor authorization. No merge releases a reservation or supplies a completed outcome.

Evaluation is bounded by the declaration limits, 17 retained merge rows per target and a 128 KiB persisted snapshot ceiling. Capacity accounting includes the current evaluation row, operation receipt and audit history. Recovery after missed synchronization is an explicit new fenced apply after provider synchronization; there is no new background reconciliation worker or live fetch in this operation. Synthetic store tests are distinct from live provider qualification, which has not been performed.

## Shared surfaces and limits

MCP exposes `agentscm_work_declarations`, `agentscm_work_declarations_set`, `agentscm_work_reconciliation` and `agentscm_work_reconciliation_apply`. Read-only tokens see only the read tools. MCP replies wrap the result in `view` and mark `evidence_omitted: true`; exact evidence remains available through HTTP and CLI. Summaries over 24 KiB omit declaration or condition lists and set `summary_complete: false`, never presenting a clipped list as exhaustive.

The Hub Work detail polls the same version-2 read, renders only `current` condition state, and labels stale or unreconciled results. It preserves the agent's report and blocker separately. Reading the page never applies reconciliation or acknowledges a reassessment. Existing catch-up audit events use the `work_pr_link` kind with explicit `declarations_set` or `reconciliation_applied` operations; these are evidence/declaration changes, not new agent reports or completions. Broad notification routing remains a separate concern; no new autonomous delivery worker is added.

No live GitHub/GitLab synchronization, installed harness session, hosted Hub, lease expiry, or production recovery qualification is claimed by these synthetic checks. There is no background reconciliation worker: synchronize provider evidence and explicitly apply with freshly read Work and declaration fences. Historical evaluations remain inspectable and never become current merely because a read succeeded.

Merged observation recovery requires retained raw `provider_number` and `provider_base_repository_id` from the provider response, matched to the requested PR and authorized stable repository identity. The lookup key alone is not provider identity evidence. Legacy tombstones without these fields remain unconfirmed until a newer qualified provider read.
