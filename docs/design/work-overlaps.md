# Agreed Work overlaps and behavior dependencies

> **Experimental alpha.** Synthetic fixtures cover SQLite and PostgreSQL, public HTTP/MCP/CLI requests and hook edit-check payloads. Installed agent sessions, two-machine delivery, live forges and deployed Hub operation remain unqualified. Git conflicts and review are separate checks.

Declare every file the task intends to edit, including a shared store file. A path overlap says where reservations meet; it does not prove conflicting changes or equivalent intent. Two leads can explicitly agree to work on named files while each retains its own reservation and responsibility. A declaration about another Work's behavior is independent of file overlap.

## Agree named files

1. Start with the full true scope. A contested start returns a durable `coordination_request` without creating the new Work. An existing lead can request a scope expansion with an ordinary fenced checkpoint; a contested expansion retains the existing scope and returns the same kind of proposal in `work_coordination_required`.
2. The holding lead reads the current request and its own Work. It calls `agentscm_work_overlap_consent` with `request_id`, `target_work_id`, `operation_id`, its native `session`, the request's `expected_updated_seq`, its Work's `target_generation` and `target_updated_seq`, and exact file `paths`. Only that current lead can grant consent. A helper, requester, owner of another Work or read-only token cannot grant it.
3. The requesting lead reads `agentscm_work_overlap_consents` using `request_id` and its own `session`. A grant's state is `awaiting_requester` until the requester explicitly accepts it. Acknowledgements, notes and ordinary split/join replies grant no permission.
4. The requester calls `agentscm_work_overlap_preflight` and `agentscm_work_overlap_start` with `{"start": WORK_START, "consent_ids": [CONSENT_ID]}`. `WORK_START` is the strict HTTP/CLI shape with `title` and `scope`, rather than the ordinary MCP start's `task` and `paths`. Preserve the original source or request key and the full proposed scope. Scope expansion uses `agentscm_work_overlap_checkpoint` with `{"checkpoint": WORK_CHECKPOINT, "consent_ids": [CONSENT_ID]}` and the checkpoint's current fences.
5. Inspect the result before editing. Accepted agreements retain visible `agreed_paths` in overview, preflight and edit-check overlap reports. Only those files are agreed; every other intersection remains contested. Shared status stops asking the two leads to settle an already agreed intersection and excludes it from unresolved-overlap attention; a third party or helper remains contested. Partial consent cannot admit the full scope. A named child file cannot waive the intersection of two directory reservations. Obtain each affected lead's consent or use split, join or handover instead.

Acceptance and reservation admission occur in one transaction. SQLite serializes the mutation with an immediate transaction; PostgreSQL uses its existing Work/capacity serialization and row fences. Concurrent identical admission returns one Work. Scope checkpoints bind the consent ID set into their existing idempotency payload; reusing an operation ID with different consent IDs is refused. Target consent alone does not admit Work, take another reservation or authorize an edit.

Consent is bound to both current leads, generations, scopes and reservation epochs. For an existing requester, the target grant captures a pending requester fence; scope changes, release/resume or expiry before acceptance require fresh target consent. Acceptance replaces that pending fence with the resulting admitted scope so exact acceptance retries remain valid. Initial admission has no requester Work yet and retains the exact proposal identity instead. Changing either scope, releasing a reservation, takeover, lease expiry or revival after expiry invalidates it. Ordinary progress and timely lease renewal preserve it. An old receipt cannot reactivate invalidated consent. Takeover does not inherit the old lead's agreement; unresolved overlaps must be coordinated again. A later decline by the target lead or withdrawal invalidates its consent. Resolved requests backing live accepted agreements survive compaction; invalidated agreements can be compacted with their request.

Supported edit guards recheck agreed files on later edits, so a formerly agreed edit cannot retain a permanent exception after invalidation. The guard's existing exact-file and warn-once behavior otherwise stays the same. Directory intent notices remain advisory, and unsupported/fail-open hooks remain subject to the existing [agent support boundaries](../agents.md). Agreement is neither a Git merge guarantee nor permission to omit scope.

## Declare behavior dependencies

Use `depends_on` with exact Work IDs even when the tasks share no paths. A start seeds the existing structured `legacy_work` prerequisite, which stays `unknown` until an evidence target is supplied. A finished Work report does not establish delivery of the required behavior. Use the existing [declarations and reconciliation](work-reconciliation.md) APIs to declare an independent `merged_pull_request` condition with an exact repository, PR number and head SHA. Only qualified retained provider merge evidence can satisfy that condition; satisfaction does not establish whole-task completion.

Preflight and start report the existing evaluator's fresh condition state. Compatibility HTTP routes include `dependencies` only with `?dependencies=1`; the CLI opts in and MCP compact replies include bounded condition lists with explicit completeness. Durable declarations govern reverse dependency reads. An explicit empty replacement removes those edges and current notice routing. A checkpoint's omission cannot remove durable conditions, and unchanged old hints cannot resurrect explicitly removed conditions. A newly added compatibility `depends_on` hint can add an unbound condition.

`agentscm_work_dependency_notices` reads the latest recorded relationship version addressed to a session that currently leads either side. Supply `session`, `after` (initially `0`), `limit` (1–100), and optional `through`; continue with the returned `next_after` and `through`. The HTTP and CLI read retain full recorded versus current state. MCP summaries bound embedded condition lists and label omitted fields. Old leads and helpers do not inherit a current lead's mailbox access.

Notice refresh occurs transactionally after an authorized Work, declaration or reconciliation mutation. The same recorded version is deduplicated. Reading or provider polling does not write a notice; after provider synchronization, an explicit reconciliation apply can record changed evidence. The mailbox retains one latest version per dependent Work (`latest_only: true`); separate page reads are not one immutable delivery (`atomic_snapshot: false`). Audit events retain earlier versions subject to existing retention. Pages are bounded to one MiB. Refresh fanout is at most 100 dependents; `coverage_complete: false` and `notification_fanout_complete: false` preserve incomplete coverage. Automatic notices do not prevent release or finish.

MCP adds a bounded advisory summary on the current lead's next writable session call, once per recorded version and existing native token/session. Its durable cursor records an attempted summary, not receipt, review or acknowledgement. Concurrent calls do not attempt the same summary twice. A lost response can be recovered with an explicit notice read from `after: 0`; that read is independent and never acknowledges anything. Pure read tools, including preflight and explicit inbox reads, do not advance this delivery cursor. A session not yet registered by a native hook or successful MCP mutator can use the explicit mailbox read; its automatic summary remains unavailable until the session is registered. There is no autonomous delivery worker or new Slack/email delivery.

## Interfaces and module decision

HTTP routes are under `/v1/hub/standup/overlap/`: `POST consent`, `GET consents?request_id=…&session=…`, `POST preflight`, `POST start` and `POST checkpoint`. Dependency notices use `GET /v1/hub/standup/dependency-notices?session=…&after=0&limit=20`. Mutations require an authenticated writable token and current lead fences; consent reads are restricted to the requester and current affected leads. New dedicated routes include dependency state; compatibility start/preflight omit it unless requested.

CLI equivalents are `agentscm work overlap-consent --request FILE`, `overlap-consents REQUEST_ID --session SESSION`, `overlap-preflight --request FILE`, `overlap-start --request FILE`, `overlap-checkpoint --request FILE` and `dependency-notices --session SESSION --after 0 --limit 20`. Request files may be `-` for stdin. The shipped coordination skill and MCP tool guidance describe the same handshake.

The new transactional SQL and helpers live in paired `store_sqlite/work_overlap.rs`, `store_pg/work_overlap.rs` and `work_dependencies.rs` modules, following the existing preflight modules. A general split of the large store files is deliberately outside this change: it would move broad unrelated scope without solving declared semantic relationships. Reservations below file level are not implemented. The system records explicit relationships and checked file authority; it does not infer semantic conflicts or duplication from source or generated judgment.
